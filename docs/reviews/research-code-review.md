# Research ZIP review: implementation techniques and Zodiac follow-ups

Reviewed 2026-10-07. This is an author-run, targeted source review of the research archives, not a line-by-line audit of those projects and not an independent review of Zodiac. The archives contain complete upstream repositories at the revisions bundled here; references below name the inspected member paths. No research archive was modified.

## Findings that match Zodiac's current design

- **Fresh data keys and authenticated encryption.** `age` wraps a random file key per recipient and authenticates streamed payload chunks (`age-main/age.go`, `age-main/x25519.go`, `age-main/internal/stream/stream.go`). `encryptor.app` also creates a random file key and authenticates chunks (`encryptor-app-main/src/core/format-v3.js`). Zodiac's one-fresh-AES-256-GCM-key-per-message, RSA-OAEP wrapping, 128-bit tag, and exact envelope ordering are the right analogue for its bounded single-message format. See `src/lib/crypto/hybrid.ts` and the envelope codec/tests. The other formats are not wire-compatible substitutes.
- **Strict parsing and bounded work.** The encryptor v3 parser validates fixed header fields and Argon2 parameter bounds before expensive work (`encryptor-app-main/src/core/format-v3.js`, `src/core/kdf.js`). Zodiac already has canonical Base64URL re-encoding, exact envelope sizes, capped input, and fixed PBES2 schema/iteration/salt bounds before PBKDF2 (`src/lib/codecs/base64url.ts`, `receiver/internal/envelope`, `receiver/internal/keyfile/pbes2.go`). Preserve these checks as one profile; do not broaden the Go loader into a general encrypted-PKCS#8 parser.
- **Authenticated completion and truncation checks.** `age` distinguishes the final stream chunk and rejects trailing bytes (`age-main/internal/stream/stream.go`). Zodiac does not stream: GCM authenticates the complete ciphertext before the CLI creates its output file, and bounded ciphertext length makes chunk framing unnecessary. If a future file/large-message feature is approved, adopt explicit final-record/truncation/trailing-data tests instead of adapting the current one-shot envelope informally.
- **Secret lifetime discipline.** `encryptor-app` centralizes best-effort byte wiping (`encryptor-app-main/src/core/bytes.js`) and uses `try/finally` around portions of key derivation and decryption (`src/core/format-v3.js`). Zodiac already clears owned plaintext/AES-key buffers and Go password/derived/decrypted buffers (`src/lib/crypto/hybrid.ts`, `receiver/internal/keyfile/pbes2.go`, `receiver/cmd/zodiac-decrypt/main.go`). Continue to describe this as best effort: JavaScript strings, `CryptoKey`, RSA big integers, runtime copies and OS memory cannot be reliably erased. Do not import `encryptor-app`'s custom streaming or password-KDF format into the current profile.
- **Key identity is a separate trust problem.** Zodiac's full SHA-256 SPKI fingerprint and out-of-band comparison guidance are stronger than silently trusting a pasted key (`src/lib/crypto/public-key.ts`, `plan.md` recipient-key section). OpenPGP's key/subkey trust and signature machinery (`openpgpjs-main/src/message.js`, `openpgpjs-main/test/security/`) and Signal's signed sender/server certificates (`libsignal-main/rust/protocol/src/sealed_sender.rs`) solve broader identity/protocol problems. They are not drop-in additions to a static recipient envelope. A fingerprint identifies bytes; it does not authenticate the recipient or sender.
- **Minimize persistent secret-bearing components.** `hat.sh` uses a service worker and posts key/password material to it (`hat.sh-master/src/components/EncryptionPanel.js`, `hat.sh-master/service-worker/sw.js`). That is a deliberate architecture choice for its streaming/file flows, but Zodiac's no-service-worker, no-storage, no-network browser boundary is simpler and easier to reason about. Do not add a worker merely to imitate its chunking.
- **Avoid overstating server-side assurances.** Yopass explicitly notes that a server cannot prove a client submitted genuinely encrypted content (`yopass-master/SECURITY.md`). PrivateBin similarly operates a network paste service (`PrivateBin-master/js/privatebin.js`). Zodiac's local-only browser flow avoids those server data paths, but a hosted operator can still replace delivered JavaScript. The existing hosted-JavaScript trust warning and verified-local-sender direction are correct; “encrypted in your browser” is not proof that a particular deployed page is honest.

## Direct source-flow comparison (2026-10-07)

This pass inspected implementation paths in the bundled archives, in addition to the project documentation. It is a targeted comparison of the checked-in snapshots, not a full audit of those upstream projects. The paths below are archive member paths, so they identify exactly what was reviewed.

- **age parser and format:** `age-main/internal/format/format.go` uses strict raw Base64 decoding, rejects CR/LF in encoded strings, bounds the header to 2 MiB, caps recipient stanzas at 1,024, and requires the 32-byte header MAC. This is a concrete example of canonical encoding and resource bounds around a flexible recipient-stanza format. Zodiac already has a simpler fixed-size/capped raw envelope and canonical Base64URL checks. Keep those checks and malformed-input tests; do not add age's visible format header or recipient stanzas to Zodiac v1, whose headerless encoding is an intentional privacy decision.
- **age key flow:** `age-main/age.go`, `age-main/x25519.go`, and `age-main/internal/stream/stream.go` implement a fresh file key, recipient key wrapping, and authenticated streaming. A fresh file key alone does not protect retained ciphertext after compromise of a reused recipient private key. Zodiac's proposed single-use RSA recipient key is intended to compartmentalize separate one-off messages. This distinction is about key lifecycle, not a claim that either construction gives ratchet-style forward secrecy.
- **encryptor.app format flow:** `encryptor-app-main/src/core/format-v3.js` generates a random 32-byte file key, wraps it under a password-derived key, derives distinct payload/header keys, authenticates the header, and encrypts data in bounded chunks. It wipes several owned intermediate buffers in `finally`/after use. The transferable lessons are explicit key separation, bounded streaming, authentication before accepting content, and disciplined best-effort cleanup. This is a password-based file format; its Argon2id/HKDF hierarchy is not a substitute for Zodiac's recipient-wrapped random message key or a reason to change the current v1 envelope.
- **OpenPGP.js decryption cleanup:** `openpgpjs-main/src/message.js` cancels the consumed encrypted stream, clears its reference, awaits successful decryption, and replaces the decrypted packet list after extracting the result. This is a useful reference for dropping references promptly. It does not guarantee erasure in JavaScript; Zodiac must continue to state that strings, runtime copies and garbage collection are outside its reliable wipe control.
- **hat.sh key and worker flow:** `hat.sh-master/src/utils/generateAsymmetricKeys.js` calls libsodium's key-exchange keypair generator and returns both private and public keys as Base64 strings. `hat.sh-master/src/components/EncryptionPanel.js` communicates with its service worker for public-key operations, and `hat.sh-master/src/components/KeyPairGeneration.js` displays/downloads generated private-key text. This supports the existing comparison: it is a different browser file-encryption workflow, and the service-worker/UI custody choices are not automatically improvements for Zodiac's no-worker boundary.
- **SOPS file flow:** `sops-main/cmd/sops/encrypt.go` reads and parses a local structured file, generates a tree data key through configured key services, encrypts the tree, and emits the encrypted document. `sops-main/aes/cipher.go` uses AES-GCM with additional authenticated data. These are useful patterns for separating data encryption from key-service wrapping and authenticating structured context, but SOPS targets managed secret files, not an anonymous one-off message envelope. Its serialization and metadata model should not be copied into Zodiac v1.
- **Implication for Zodiac:** These source paths reinforce existing decisions rather than reveal a missing primitive. The specific follow-ups remain the already-tracked REC-04 single-use recipient-key lifecycle and opt-in best-effort output/key cleanup, careful cleanup of owned references/buffers, and the independent integrated review and signed-release gates. No new wire-format, algorithm, or host architecture change is justified by this comparison. A fingerprint/key-verification step remains essential: encryption to a substituted public key will protect the message for the wrong recipient.

## Useful techniques that do not fit the current protocol

- **Password-derived file encryption:** encryptor.app and hat.sh use Argon2id/libsodium for passphrase-oriented file encryption. That addresses a different key-establishment problem. Zodiac's message key is uniformly random and recipient-wrapped; its passphrase only protects the recipient's local private-key file. Do not substitute a password KDF for RSA wrapping or weaken the RSA profile to match those projects.
- **Ratchets, forward secrecy, and post-quantum protection:** Signal/libsignal and SimpleX implement interactive, stateful messaging protocols. Their key rotation, ratchets, metadata protections, padding and out-of-band setup cannot be grafted onto one-shot RSA ciphertext. Zodiac correctly documents that static RSA has no forward secrecy and is not post-quantum.
- **Streaming/chunked AEAD:** age and C2SP chunked encryption provide bounded-memory, truncation-aware large-file designs. Zodiac currently caps messages at 64 KiB and authenticates one complete message. Treat chunking as a separately specified future format, not a performance tweak to this envelope.
- **Encrypted metadata/MACs:** encryptor v3 and SOPS authenticate structured headers or encrypted document state. Zodiac's compatible envelope intentionally has no version/key-id/metadata header; fingerprints, symbol labels, and transcription checks are external and must not be described as authenticated by the ciphertext. A future versioned format could bind a version, suite, recipient identifier, and declared lengths as AEAD associated data, but it would need a new format identifier, compatibility plan, vectors, independent review, and migration policy. Do not alter v1 bytes.
- **Public-key formats and signature ecosystems:** OpenPGP/GnuPG support certifications, subkeys, algorithm negotiation and legacy interoperability. Zodiac deliberately accepts one canonical SPKI RSA public key and one encrypted PKCS#8 private-key profile. Broadening accepted syntax increases parser surface and is not a security improvement by itself.

## Concrete gaps and follow-up

1. **Publish a private vulnerability-reporting policy before public release.** The inspected OpenPGP.js, Signal/libsignal, PrivateBin, encryptor.app, hat.sh, Signal Server, and Yopass archives each provide a private reporting route (their `SECURITY.md` files or project README). Zodiac has release/trust and incident-owner gates, but no `SECURITY.md` or chosen public reporting route. A new SEC-04.4 item now tracks selecting a route and owner, documenting scope/supported versions, and avoiding an invented contact or response SLA. This does not mean an audit has happened.
2. **Keep release verification independent of the download host.** SOPS documents signed tags, Cosign-signed checksums and provenance (`sops-main/docs/release.md`). Signal Desktop documents reproducible-build work and its platform limits (`Signal-Desktop-main/reproducible-builds/README.md`). These are useful release goals, not proof that Zodiac can immediately reproduce every target. Zodiac already gates signing, publisher identity, independent hashes/channel and reviewed sender bytes; those remain genuine release blockers.
3. **Retain explicit cross-implementation vectors and negative tests.** The encryptor v3 spec requires test vectors across implementations; age has stream and format tests; OpenPGP.js keeps dedicated security regression tests. Zodiac's Chromium/Firefox WebCrypto ↔ Go interoperability, malformed/canonical input tests, tamper cases, OpenSSL fixtures, and receiver fuzz/resource gates are strong matches. Keep each wire-format and parser change tied to independent-oracle tests; the user-requested CI workflow remains inactive by choice, so local passing evidence is not published CI evidence.
4. **Keep metadata and user exports in the threat model.** SimpleX's privacy policy spells out what relay operators, push providers and local devices can observe (`simplex-chat-stable/PRIVACY.md`). Its network model differs substantially, but the useful practice is to name each observer and each residual disclosure. Zodiac already documents length leakage, browser-host trust, deliberate exports, clipboard/print persistence, and recipient custody. Recheck those statements against actual Vercel access logs, deployed headers, and first-time user flows at release; source-only tests cannot establish provider behavior.
5. **Preserve strict fixed profiles and document the limits of local key-file encryption.** Zodiac's PBES2/CBC receiver profile is unauthenticated at the container layer, with generic unlock failures and strict bounds. Keep the current exact profile, uniform padding scan, native OpenSSL fixtures/oracle, and focused review gate. The samples do not justify accepting more PBES2 variants or claiming the container is authenticated.

## Envelope decision (2026-10-07)

- **Decision:** Preserve the compatible v1 raw envelope without a version byte, algorithm identifier, key ID/recipient ID, magic header, or length field. Its fixed RSA-OAEP-SHA-256 + AES-256-GCM suite and headerless encoding are intentional design choices, not omissions to repair in v1.
- The absence of an explicit recipient identifier reduces direct reader identification from the envelope itself. It does not promise anonymity: ciphertext length, the sender/recipient context, and external delivery metadata can still disclose information.
- No v2 or algorithm transition is currently planned. If a future algorithm or wire-format transition becomes necessary, define a separately versioned format, migration and interoperability policy, test vectors, and independent review before implementation. Do not make a time-bound claim that RSA-4096 remains safe until quantum computers reach a particular capability.

### One-off message keys versus ratcheting

For Zodiac’s intended one-off message, a ratchet is not required. The sender already generates a fresh, independent random AES-256 key for each envelope and wraps it to the recipient RSA public key. In an optional single-use mode, that one-time RSA pair is the recipient key for that message; there is no separate regular recipient key that must be evolved or involved. The sender does not derive the message key from an earlier message key.

A ratchet addresses a different problem: a multi-message session evolves chain state to derive message keys and can mix fresh DH material at ratchet steps. Its past-message protection depends on old key state becoming unavailable, just as the proposed single-use workflow depends on retiring that message’s private key. These approaches are not equivalent, but ratcheting is not inherently more secure for a one-message exchange. Single-use RSA compartmentalizes messages across distinct private keys; later compromise of one single-use key does not expose ciphertexts encrypted to other keys, assuming keys were not reused or copied. Best-effort deletion can reduce residual local exposure but cannot guarantee that a key copy is unavailable. The meaningful next work is a reliable one-message key lifecycle: generate offline, verify the public/private pair and fingerprint, deliver only the public key, decrypt the intended message, and retire the private key after successful output/read. Keep static-key use supported with its historical-ciphertext compromise warning. No change to the v1 envelope or cryptographic algorithms is needed for this workflow.

## Receiver cleanup and single-use-key follow-up (2026-10-07)

- The supplied `securefiledelete.png` shows a C# routine with seven passes (zero, `0xFF`, and five random data writes), three random same-directory `File.Move` operations, then deletion retries. In the shown code, `systemWriteCacheEnabled` is `true`, selecting `FileOptions.None`; it does not enable write-through or unbuffered I/O. The user reports separate production/raw-hex testing; that remains user-reported, configuration-specific evidence, not an independent project verification.

REC-04 now adapts this flow in Windows Go: seven bounded writes with fresh random chunks, flush per pass, logical-volume sector plus file/device alignment, `FILE_NO_INTERMEDIATE_BUFFERING` and write-through, then three random same-directory renames through the held file handle and handle-based deletion. Local Windows tests pass on the current workspace volume. This verifies the tested filesystem/runtime path only; no raw-sector/SSD guarantee or independent review is implied. Three renames do not prove old NTFS MFT names or journal records are overwritten. The implementation stays best effort, and snapshots, remapped blocks, backups, paging, or other copies can persist.

- The intended recipient workflow is file output to preserve the decrypted message's exact formatting, followed by best-effort cleanup of the plaintext output and, when explicitly using a single-use recipient key, the encrypted private-key file after successful decryption. A timeout or user keypress can trigger cleanup. Keep file output as the default; do not print plaintext to the terminal. Preserve static-key support and never automatically delete a static key.
- Cleanup must be an explicit receiver option or explicit single-use-key workflow, report success/failure, and never describe the result as guaranteed physical erasure. A compromise of the recipient computer remains out of scope; cleanup reduces residual local exposure but cannot defeat an attacker controlling the machine or recover copies already made.
- Windows `FILE_FLAG_WRITE_THROUGH`/`FILE_FLAG_NO_BUFFERING` may affect cache/write behavior, but are not proof that old SSD flash cells, filesystem metadata, VSS or third-party snapshots, backups, sync copies, paging, or other copies were erased. No-buffering has alignment requirements. `FILE_FLAG_OPEN_REPARSE_POINT` can support safe path handling; it does not sanitize storage. The receiver's `QueryDosDevice` check only looks for shadow-copy device names exposed to the current process; it cannot enumerate or prove the absence of every VSS snapshot, and it cannot associate a detected device with the selected files. Microsoft documents the write/caching scope and alignment constraints in [File Buffering](https://learn.microsoft.com/en-us/windows/win32/fileio/file-buffering) and [CreateFile flags](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea); its [SDelete guidance](https://learn.microsoft.com/en-us/sysinternals/downloads/sdelete) describes filesystem cases where overwriting cannot remove prior data. [VSS documentation](https://learn.microsoft.com/en-us/windows-server/storage/file-server/volume-shadow-copy-service) describes copy-on-write snapshots. [NIST SP 800-88 Rev. 2](https://csrc.nist.gov/pubs/sp/800/88/r2/final) frames sanitization as a media-specific process rather than a generic file-delete guarantee.
- A fresh RSA pair for one message is a recommended optional workflow, not a new cryptographic forward-secrecy claim. It can reduce the historical exposure from later compromise of a routinely reused private key if the one-time private key and all copies are removed after successful decryption. It cannot protect a ciphertext if the one-time private key was copied before cleanup, and it does not change the v1 envelope or provide Signal-style ratcheting. Static recipients must be told that later compromise of their long-term key can expose retained ciphertext.
- Age/SOPS/PGP are not forward-secrecy solutions for this static-envelope use case. Their code, test, parser, release, and operational practices remain useful research references, but maturity alone does not mean they meet this particular property. Signal's ratchet is a distinct stateful messaging protocol; storing ciphertext on disk does not itself negate ratchet-derived forward secrecy.
- Follow-up: REC-04 now implements the single-use-key workflow, opt-in best-effort plaintext/key-file cleanup, and a non-elevated `QueryDosDevice` shadow-copy device-name advisory. The probe may miss snapshots and cannot establish whether a detected device contains either selected file; it must never be described as proof of absence or sanitization. Independent review and additional documented-platform evidence remain open.

## One-off email trust assessment and web architecture (2026-10-08)

This is a qualitative, use-case-specific assessment for sending one very confidential message as email ciphertext. It is not a security certification or a claim that any project is safe for every threat model.

### Comparative trust and fit

- **age is my first choice today** when both parties can use a verified, current offline release and verify the recipient identity. Its format and implementation provide a compact recipient-oriented file workflow, strict decoding/parser limits, and independent implementation/testing work. The current age format specification includes an X-Wing ML-KEM-768 + X25519 hybrid recipient type; whether that option is usable depends on the exact sender/receiver versions and must be confirmed with an interoperability test. The format's 128-bit symmetric file key and its recipient-key lifecycle differ from Zodiac, so the comparison is about end-to-end tool assurance and capabilities, not identical algorithms. See `age-main/internal/format/format.go`, `age-main/x25519.go`, and the [age format specification](https://github.com/C2SP/C2SP/blob/main/age.md).
- **GnuPG/OpenPGP is my second choice today** when the users can correctly manage and verify keys. Its main advantage for this use case is the mature operational ecosystem: fingerprints, key certifications, revocation/expiration practices, and optional signing. Encryption alone does not authenticate the sender; a verified signature can. Use a current release from a source whose authenticity you verify. As of this review, the upstream download page lists GnuPG 2.5.24 as stable, while the upstream branch note says its post-quantum support is not yet complete. OpenPGP is a protocol/ecosystem, not a single implementation; OpenPGP.js is a library and cannot be ranked as a standalone end-user product without specifying its application, integration, and release channel. See `gnupg-master/g10/encrypt.c`, `gnupg-master/g10/decrypt.c`, `openpgpjs-main/src/message.js`, [GnuPG releases](https://gnupg.org/download/index.html), and [GnuPG branch status](https://gnupg.org/blog/20250827-new-repository.html).
- **Zodiac is a promising future third choice by product fit, but is not third in current trust.** The sender still labels itself a development build for synthetic messages; QA-03 integrated independent review, trusted release verification, and REC-04's complete one-time-key lifecycle remain open. Until those gates pass, I would not recommend Zodiac for real secrets. After they pass, I would consider it for this specific one-off workflow, without assuming an audit proves the absence of defects or that Zodiac thereby outranks age/GnuPG.
- **encryptor.app and hat.sh** are browser-based file-encryption tools with different password/key and worker architectures. **PrivateBin** adds a hosted paste service and its server/metadata/availability trust boundary. These are not directly rankable against a local recipient-key email flow without fixing exact versions and delivery modes. For sensitive email specifically, I place these in a lower-confidence/less-direct-fit tier than mature offline age/GnuPG releases, rather than claim a precise order between them. **SOPS** is for structured secrets/configuration workflows, not a peer one-off message product.

### Zodiac's cryptographic construction

The inspected sender source (`src/lib/crypto/hybrid.ts`, `src/lib/crypto/profile.ts`, and `src/lib/codecs/envelope.ts`) uses a fresh 32-byte random AES key per message, RSA-OAEP with SHA-256 to wrap that key, and AES-256-GCM with a 12-byte nonce and 128-bit tag. WebCrypto's RSA-OAEP profile uses MGF1 with the key's SHA-256 hash and the configured empty label. The wrapped key and nonce are bound as GCM additional authenticated data. The envelope preserves the fixed `wrappedKey || nonce || tag || ciphertext` ordering and authenticates the whole bounded message before plaintext output. This is a sound conventional hybrid-encryption construction when implemented correctly; its components and roles match WebCrypto, RSAES-OAEP, and GCM specifications. See [W3C WebCrypto](https://www.w3.org/TR/webcrypto/), [RFC 8017](https://www.rfc-editor.org/rfc/rfc8017/), and [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final).

This construction does not authenticate the sender: anyone with the recipient's public key can create a valid ciphertext. The GCM tag provides ciphertext integrity to the recipient, not a sender identity claim. It is also not post-quantum. If a static recipient RSA private key is later compromised, saved ciphertexts encrypted to it may be recovered. A dedicated single-use recipient key can compartmentalize distinct messages if it was not copied/reused and its private material is genuinely unavailable after use; best-effort file deletion cannot guarantee that. This is message-level key lifecycle, not a conversation ratchet and not a formal forward-secrecy guarantee. Keep the v1 envelope headerless as decided; do not change its bytes based on this assessment.

### Web application security boundary

The current architecture has good defense-in-depth properties: static Astro/Svelte output, native WebCrypto, a public-key-only sender, and no application API, database, analytics, service worker, or persistent message/key storage. `config/security-policy.ts` denies connections, workers, objects and form submission, blocks inline script/style attributes, and limits resource types. Keep production-build DOM/CSP checks and avoid adding remote scripts, fonts, analytics, or crypto services.

The CSP also includes `'self'` in `script-src` and `style-src`, so same-origin resources remain trusted; hashes do not independently authenticate every deployed asset. A compromised hosting account, build pipeline, origin, or maliciously updated deployment could serve JavaScript that reads plaintext before encryption. CSP is an injection-mitigation layer, not protection against a malicious trusted origin. For sensitive use when the host is not trusted, the user needs an independently verified local sender artifact/hash through a separate trusted channel before typing the message. The EN-04 offline artifact and REL-03 verification work remain relevant. OWASP likewise describes CSP as defense in depth alongside secure development, not a substitute for it: [OWASP CSP guidance](https://cheatsheetseries.owasp.org/cheatsheets/Content_Security_Policy_Cheat_Sheet.html).

### Transferable lessons and open work

1. Retain age's canonical decoding, explicit parser/resource bounds, format tests, and independent interoperability vectors. Zodiac already has these controls for its simpler fixed envelope; continue testing them rather than importing age's format header/recipient-stanza design into headerless v1.
2. Retain GnuPG/OpenPGP's emphasis on independently verifying recipient key identity and supporting sender authentication as a separate feature. Fingerprints identify key bytes but are only meaningful when compared over a trusted independent channel. A signature feature would need to address sender identity disclosure, key custody, format compatibility, and review.
3. Complete REC-04's explicit single-use recipient key lifecycle, with opt-in best-effort cleanup only after successful authenticated output, preserving static-key support and clearly reporting cleanup limits.
4. Complete QA-03 independent integrated review and REL-03 signed/verifiable artifact and publisher-channel gates. Passing author-run tests or a review packet alone is not an external audit or trusted release.
5. Plan algorithm agility and post-quantum migration before it becomes urgent. Archived ciphertext can be collected now and decrypted later if RSA is broken; waiting until that break to plan migration would not protect old captures. Any future wire change requires its own specification, interop vectors, compatibility policy, and review, while v1 remains unchanged.

### Email delivery and metadata

With Zodiac, age, or GnuPG, email carries ciphertext, but ordinary email still exposes routing and timing metadata and often the subject. Gmail's documented client-side encryption leaves headers, including subject, timestamp, and recipients, outside that added encryption; it is also limited to eligible Workspace configurations. Proton-to-Proton messages are end-to-end encrypted, while Proton-to-external-provider mail is not end-to-end encrypted by default unless using a supported password-protected or PGP flow. A VPN shifts network-observer trust; it does not encrypt mail contents end-to-end from the email provider. Use generic subjects and minimize identifying metadata. See [Gmail CSE limits](https://support.google.com/mail/answer/13317990?hl=en), [Proton encryption details](https://proton.me/support/proton-mail-encryption-explained), and [Proton PGP guidance](https://proton.me/support/how-to-use-pgp).

## Practical takeaways and backlog coverage (2026-10-08)

The current engineering evidence supports the conventional hybrid-encryption design, but does not establish product-level readiness for very confidential messages. The format authenticates ciphertext against tampering and requires the recipient private key; it does not authenticate the sender. Static RSA keys create harvest-now/decrypt-later exposure if the private key is later compromised. A dedicated, genuinely single-use RSA pair can compartmentalize messages, but does not provide a ratchet or guaranteed erasure. The v1 envelope remains intentionally headerless and unchanged.

The actionable work is already represented in the backlog, with these distinctions: **REC-04** is planned but not implemented; **QA-03**, **REL-03**, and **SEC-04** remain open review/release/trust-anchor gates; **E08/QA-02** still need human, accessibility/device, and Gmail-primary (Outlook-secondary) trials; **EN-04** still needs final offline-sender delivery selection and independent verification. These are prerequisites to reconsidering Zodiac for real confidential use, not completed endorsements.

**FUT-02** remains deferred and does not authorize a v1 algorithm or envelope change. Its scope now explicitly requires assessing harvest-now/decrypt-later against the message confidentiality lifetime and setting review/migration triggers before RSA is practically breakable; planning must not wait for a break. No v2 schedule or migration decision has been made.

Practical use guidance remains: prefer a verified, current age or GnuPG release for real secrets today; treat Zodiac as development/research until integrated independent review, release trust, and operational trials are complete. For any email ciphertext, minimize subject and identifying metadata; a VPN does not conceal contents from the mail provider.

## Deferred sender authentication decision (2026-10-08)

The user selected a future optional per-message Ed25519 sign-then-encrypt flow for Zodiac. The sender may choose to sign a message before the existing encryption step; the signature and signed content will be inside the encrypted plaintext. The Go receiver will later decrypt, strictly parse the signed profile, and verify the signature against a sender public key whose identity was verified independently. The sender page must explain the choice and its identity/privacy tradeoff.

Keep the current unsigned v1 flow and envelope unchanged. Do not treat an embedded signer key or a valid signature as proof of identity. Verification of both the intended recipient key and, when signatures are used, the sender key must be explicit and tied to a trusted separate channel. An inner signature hides signer identity from the email provider, but the recipient can identify the signer and retains durable evidence; this can reduce deniability.

This is tracked as deferred FUT-10, not implemented or approved for v1. It requires a separately versioned/bounded signed-plaintext profile and encoding, native WebCrypto Ed25519 in the sender and Go standard-library Ed25519 in the receiver (no external crypto libraries), cross-implementation tests, signature-stripping/downgrade handling, and independent review. Long-term signing private-key custody is a release blocker for the feature: do not place it in mutable hosted JavaScript for sensitive signing; use the independently verified local sender or another reviewed custody design. Keep signing keys separate from recipient-encryption and release-signing keys.

For current real one-off messages that require sender authenticity, the review recommendation remains verified GnuPG/OpenPGP signed-then-encrypted. For confidentiality without sender identity, age remains the preferred current tool. Zodiac remains development/research until its independent review and release trust gates close.

## Public-key versus password-based confidentiality clarification (2026-10-08)

The user emphasized that Zodiac's recipient-specific asymmetric workflow has a practical confidentiality advantage over password-encrypted archives: the sender can encrypt using a recipient public key, without distributing the decryption secret alongside the ciphertext. The recipient's RSA private key is generated cryptographically rather than chosen by a person, and Zodiac creates a fresh uniformly random 32-byte AES message key for each encryption. This avoids password guessing as the message-key establishment mechanism and avoids a separate shared-message-password delivery channel. This is an advantage in key distribution and in avoiding human-selected low-entropy passwords; it does not make asymmetric encryption categorically stronger in every threat model.

Keep the strength comparison precise: RSA-4096 denotes the modulus size, not 4096 bits of security; the RSA private key's protection depends on the implementation and custody, and the public key must be verified as belonging to the intended recipient. A password is not inherently weak: a genuinely random, sufficiently high-entropy password can resist guessing, whereas a human-created password may not. A KDF slows offline guesses but cannot add entropy to the password. The 7z format's documented design uses AES-256 with an iterated SHA-256 password derivation, not Argon2; its AES mode is CBC. Zodiac uses AES-256-GCM for authenticated encryption, wrapping its fresh AES key with RSA-OAEP. These are different constructions with different distribution, integrity, and long-term quantum tradeoffs. See the [7-Zip format description](https://www.7-zip.org/7z.html), [7-Zip method list](https://github.com/ip7z/7zip/blob/main/DOC/Methods.txt), and [NIST post-quantum FAQ](https://csrc.nist.gov/Projects/post-quantum-cryptography/faqs).

AES-256 is not the present quantum weak point: known quantum search offers a constrained advantage, and NIST expects AES-256 to remain safe for a long time. RSA is the part vulnerable to a sufficiently capable quantum computer. Consequently, ciphertext captured today could face harvest-now/decrypt-later exposure if RSA becomes practically breakable while the private key remains recoverable. A truly single-use RSA pair can reduce cross-message exposure from later compromise of a reused key, but does not make RSA post-quantum or erase archived captures. A future post-quantum migration would primarily replace or hybridize key establishment while retaining a reviewed symmetric AEAD such as AES-256-GCM; it requires a separately specified format, browser/Go interoperability, and independent review. No v1 change or v2 schedule is authorized by this clarification.

The practical assessment is therefore conditional: with a verified recipient key and conventional near-term attackers, Zodiac's public-key delivery plus fresh random AES key and GCM tamper detection has meaningful advantages over sending a password-protected 7z archive. For confidentiality against future quantum RSA attacks, symmetric encryption with a truly random high-entropy password avoids that particular RSA exposure, at the cost of safely delivering and protecting the shared password and the different integrity behavior of 7z CBC. Neither construction eliminates endpoint compromise, key substitution, or metadata leakage. This comparison is a threat-model clarification, not a claim that Zodiac is independently audited or universally safer.

## Practical trust recommendation and improvement work (2026-10-08)

For an exceptionally confidential one-off message, the recommendation is conditional on key verification, sender-authentication needs, and how long the message must remain secret. If sender identity matters, use a verified GnuPG/OpenPGP signing key and verified recipient key, then sign and encrypt; the recipient can verify the signer, and the signature is durable evidence that may reduce deniability. If sender identity is not needed, age is a suitable simple offline public-key option after independently verifying the recipient key. Its ordinary X25519 recipient mode is not post-quantum; any hybrid ML-KEM recipient should be evaluated in the exact released version and receiver implementation before relying on it. For long-term quantum confidentiality where password sharing is acceptable, a high-entropy randomly generated 7z password shared through a separate end-to-end encrypted channel avoids RSA's quantum exposure, while retaining the distinct CBC integrity tradeoff. These are threat-model choices, not a universal product ranking or a claim that maturity alone proves security.

Zodiac's public-key delivery has a concrete advantage over a password archive: the sender can encrypt to the recipient's public key without sending a shared message password. Zodiac uses a fresh random 32-byte AES key and AES-256-GCM authentication, with RSA-OAEP wrapping. For a verified recipient key and conventional near-term attacker, this is a strong, appropriate construction. The present reason not to prefer Zodiac for a very high-consequence secret is the assurance around the complete system and release (independent review, externally verifiable artifacts/origin, key-identity workflow, and operational trials), plus RSA's harvest-now/decrypt-later exposure for long-lived secrets—not a weakness in AES-256-GCM. A 4096-bit RSA modulus is not 4096-bit security. No available option protects a compromised endpoint or prevents all email metadata leakage.

Improvement disposition: keep v1 and its exact envelope unchanged. Close QA-03 independent system review and SEC-04 release-trust gates; make out-of-band recipient fingerprint verification explicit for sensitive custom-key use; complete REC-04's optional genuinely single-use RSA lifecycle with honestly limited best-effort cleanup claims; and retain FUT-10 as deferred optional sign-then-encrypt, with separately verified signer identity and reviewed key custody. FUT-02 already covers the required separately versioned future protocol/PQ assessment; refine its acceptance scope to compare hybrid ML-KEM key establishment with conventional RSA/ECC, retain AES-GCM if appropriate, evaluate browser-native WebCrypto and Go interoperability under the no-external-browser-crypto-library constraint, assess downgrade/compatibility policy, and define migration triggers against confidentiality lifetime. Do not treat a one-time RSA pair as post-quantum protection, forward secrecy, or guaranteed erasure, and do not commit a v2 date.
