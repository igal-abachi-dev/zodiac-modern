# Research ZIP review: implementation techniques and Zodiac follow-ups

Reviewed 2026-10-07. This is an author-run, targeted source review of the research archives, not a line-by-line audit of those projects and not an independent review of Zodiac. The archives contain complete upstream repositories at the revisions bundled here; references below name the inspected member paths. No research archive was modified.

## Findings that match Zodiac's current design

- **Fresh data keys and authenticated encryption.** `age` wraps a random file key per recipient and authenticates streamed payload chunks (`age-main/age.go`, `age-main/x25519.go`, `age-main/internal/stream/stream.go`). `encryptor.app` also creates a random file key and authenticates chunks (`encryptor-app-main/src/core/format-v3.js`). Zodiac's one-fresh-AES-256-GCM-key-per-message, RSA-OAEP wrapping, 128-bit tag, and exact envelope ordering are the right analogue for its bounded single-message format. See `src/lib/crypto/hybrid.ts` and the envelope codec/tests. The other formats are not wire-compatible substitutes.
- **Strict parsing and bounded work.** The encryptor v3 parser validates fixed header fields and Argon2 parameter bounds before expensive work (`encryptor-app-main/src/core/format-v3.js`, `src/core/kdf.js`). Zodiac already has canonical Base64URL re-encoding, exact envelope sizes, capped input, and fixed PBES2 schema/iteration/salt bounds before PBKDF2 (`src/lib/codecs/base64url.ts`, `receiver/internal/envelope`, `receiver/internal/keyfile/pbes2.go`). Preserve these checks as one profile; do not broaden the Go loader into a general encrypted-PKCS#8 parser.
- **Authenticated completion and truncation checks.** `age` distinguishes the final stream chunk and rejects trailing bytes (`age-main/internal/stream/stream.go`). Zodiac does not stream: GCM authenticates the complete ciphertext before the CLI creates its output file, and bounded ciphertext length makes chunk framing unnecessary. If a future file/large-message feature is approved, adopt explicit final-record/truncation/trailing-data tests instead of adapting the current one-shot envelope informally.
- **Secret lifetime discipline.** `encryptor-app` centralizes best-effort byte wiping (`encryptor-app-main/src/core/bytes.js`) and uses `try/finally` around portions of key derivation and decryption (`src/core/format-v3.js`). Zodiac already clears owned plaintext/AES-key buffers and Go password/derived/decrypted buffers (`src/lib/crypto/hybrid.ts`, `receiver/internal/keyfile/pbes2.go`, `receiver/cmd/zodiac-decrypt/main.go`). Continue to describe this as best effort: JavaScript strings, `CryptoKey`, RSA big integers, runtime copies and OS memory cannot be reliably erased. Do not import `encryptor-app`'s custom streaming or password-KDF format into the current profile.
- **Key identity is a separate trust problem.** Zodiac's full SHA-256 SPKI fingerprint and out-of-band comparison guidance are stronger than silently trusting a pasted key (`src/lib/crypto/public-key.ts`, `plan.md` recipient-key section). OpenPGP's key/subkey trust and signature machinery (`openpgpjs-main/src/message.js`, `openpgpjs-main/test/security/`) and Signal's signed sender/server certificates (`libsignal-main/rust/protocol/src/sealed_sender.rs`) solve broader identity/protocol problems. They are not drop-in additions to a static recipient envelope. A fingerprint identifies bytes; it does not authenticate the recipient or sender.
- **Minimize persistent secret-bearing components.** `hat.sh` uses a service worker and posts key/password material to it (`hat.sh-master/src/components/EncryptionPanel.js`, `hat.sh-master/service-worker/sw.js`). That is a deliberate architecture choice for its streaming/file flows, but Zodiac's no-service-worker, no-storage, no-network browser boundary is simpler and easier to reason about. Do not add a worker merely to imitate its chunking.
- **Avoid overstating server-side assurances.** Yopass explicitly notes that a server cannot prove a client submitted genuinely encrypted content (`yopass-master/SECURITY.md`). PrivateBin similarly operates a network paste service (`PrivateBin-master/js/privatebin.js`). Zodiac's local-only browser flow avoids those server data paths, but a hosted operator can still replace delivered JavaScript. The existing hosted-JavaScript trust warning and verified-local-sender direction are correct; “encrypted in your browser” is not proof that a particular deployed page is honest.

## Useful techniques that do not fit the current protocol

- **Password-derived file encryption:** encryptor.app and hat.sh use Argon2id/libsodium for passphrase-oriented file encryption. That addresses a different key-establishment problem. Zodiac's message key is uniformly random and recipient-wrapped; its passphrase only protects the recipient's local private-key file. Do not substitute a password KDF for RSA wrapping or weaken the RSA profile to match those projects.
- **Ratchets, forward secrecy, and post-quantum protection:** Signal/libsignal and SimpleX implement interactive, stateful messaging protocols. Their key rotation, ratchets, metadata protections, padding and out-of-band setup cannot be grafted onto one-shot RSA ciphertext. Zodiac correctly documents that static RSA has no forward secrecy and is not post-quantum.
- **Streaming/chunked AEAD:** age and C2SP chunked encryption provide bounded-memory, truncation-aware large-file designs. Zodiac currently caps messages at 64 KiB and authenticates one complete message. Treat chunking as a separately specified future format, not a performance tweak to this envelope.
- **Encrypted metadata/MACs:** encryptor v3 and SOPS authenticate structured headers or encrypted document state. Zodiac's compatible envelope intentionally has no version/key-id/metadata header; fingerprints, symbol labels, and transcription checks are external and must not be described as authenticated by the ciphertext. A future versioned format could bind a version, suite, recipient identifier, and declared lengths as AEAD associated data, but it would need a new format identifier, compatibility plan, vectors, independent review, and migration policy. Do not alter v1 bytes.
- **Public-key formats and signature ecosystems:** OpenPGP/GnuPG support certifications, subkeys, algorithm negotiation and legacy interoperability. Zodiac deliberately accepts one canonical SPKI RSA public key and one encrypted PKCS#8 private-key profile. Broadening accepted syntax increases parser surface and is not a security improvement by itself.

## Concrete gaps and follow-up

1. **Publish a private vulnerability-reporting policy before public release.** The inspected OpenPGP.js, Signal/libsignal, PrivateBin, encryptor.app, hat.sh, Signal Server, and Yopass archives each provide a private reporting route (their `SECURITY.md` files or project README). Zodiac has release/trust and incident-owner gates, but no `SECURITY.md` or chosen public reporting route. A new SEC-04.4 item now tracks selecting a route and owner, documenting scope/supported versions, and avoiding an invented contact or response SLA. This does not mean an audit has happened.
2. **Keep release verification independent of the download host.** SOPS documents signed tags, Cosign-signed checksums and provenance (`sops-main/docs/release.md`). Signal Desktop documents reproducible-build work and its platform limits (`Signal-Desktop-main/reproducible-builds/README.md`). These are useful release goals, not proof that Zodiac can immediately reproduce every target. Zodiac already gates signing, publisher identity, independent hashes/channel and reviewed sender bytes; those remain genuine release blockers.
3. **Retain explicit cross-implementation vectors and negative tests.** The encryptor v3 spec requires test vectors across implementations; age has stream and format tests; OpenPGP.js keeps dedicated security regression tests. Zodiac's Chromium/Firefox WebCrypto ↔ Go interoperability, malformed/canonical input tests, tamper cases, OpenSSL fixtures, and receiver fuzz/resource gates are strong matches. Keep each wire-format and parser change tied to independent-oracle tests; the user-requested CI workflow remains inactive by choice, so local passing evidence is not published CI evidence.
4. **Keep metadata and user exports in the threat model.** SimpleX's privacy policy spells out what relay operators, push providers and local devices can observe (`simplex-chat-stable/PRIVACY.md`). Its network model differs substantially, but the useful practice is to name each observer and each residual disclosure. Zodiac already documents length leakage, browser-host trust, deliberate exports, clipboard/print persistence, and recipient custody. Recheck those statements against actual Vercel access logs, deployed headers, and first-time user flows at release; source-only tests cannot establish provider behavior.
5. **Preserve strict fixed profiles and document the limits of local key-file encryption.** Zodiac's PBES2/CBC receiver profile is unauthenticated at the container layer, with generic unlock failures and strict bounds. Keep the current exact profile, uniform padding scan, native OpenSSL fixtures/oracle, and focused review gate. The samples do not justify accepting more PBES2 variants or claiming the container is authenticated.

## Receiver cleanup and single-use-key follow-up (2026-10-07)

- The user reports that the `securefiledelete.png` overwrite/delete routine was derived from Microsoft SDelete and tested in production, including inspection with a raw hex editor on the tested drives. This is valuable user-reported, configuration-specific evidence that overwrite cleanup can improve on ordinary deletion. It has not been independently reproduced or reviewed in this repository, so record it as user-reported evidence rather than a project verification result.
- The intended recipient workflow is file output to preserve the decrypted message's exact formatting, followed by best-effort cleanup of the plaintext output and, when explicitly using a single-use recipient key, the encrypted private-key file after successful decryption. A timeout or user keypress can trigger cleanup. Keep file output as the default; do not print plaintext to the terminal. Preserve static-key support and never automatically delete a static key.
- Cleanup must be an explicit receiver option or explicit single-use-key workflow, report success/failure, and never describe the result as guaranteed physical erasure. A compromise of the recipient computer remains out of scope; cleanup reduces residual local exposure but cannot defeat an attacker controlling the machine or recover copies already made.
- Windows `FILE_FLAG_WRITE_THROUGH`/`FILE_FLAG_NO_BUFFERING` may affect cache/write behavior, but are not proof that old SSD flash cells, filesystem metadata, VSS or third-party snapshots, backups, sync copies, paging, or other copies were erased. No-buffering has alignment requirements. `FILE_FLAG_OPEN_REPARSE_POINT` can support safe path handling; it does not sanitize storage. A VSS check may report detected snapshots as an advisory, but a clean result cannot prove that no snapshots or other copies exist. Microsoft documents the write/caching scope and alignment constraints in [File Buffering](https://learn.microsoft.com/en-us/windows/win32/fileio/file-buffering) and [CreateFile flags](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea); its [SDelete guidance](https://learn.microsoft.com/en-us/sysinternals/downloads/sdelete) describes filesystem cases where overwriting cannot remove prior data. [VSS documentation](https://learn.microsoft.com/en-us/windows-server/storage/file-server/volume-shadow-copy-service) describes copy-on-write snapshots. [NIST SP 800-88 Rev. 2](https://csrc.nist.gov/pubs/sp/800/88/r2/final) frames sanitization as a media-specific process rather than a generic file-delete guarantee.
- A fresh RSA pair for one message is a recommended optional workflow, not a new cryptographic forward-secrecy claim. It can reduce the historical exposure from later compromise of a routinely reused private key if the one-time private key and all copies are removed after successful decryption. It cannot protect a ciphertext if the one-time private key was copied before cleanup, and it does not change the v1 envelope or provide Signal-style ratcheting. Static recipients must be told that later compromise of their long-term key can expose retained ciphertext.
- Age/SOPS/PGP are not forward-secrecy solutions for this static-envelope use case. Their code, test, parser, release, and operational practices remain useful research references, but maturity alone does not mean they meet this particular property. Signal's ratchet is a distinct stateful messaging protocol; storing ciphertext on disk does not itself negate ratchet-derived forward secrecy.
- Follow-up: update REC-02 with an unimplemented, tested task for opt-in plaintext/key-file best-effort cleanup and optional snapshot warnings. Before implementation, update the receiver plan/privacy wording and define cancellation, timeout, success/failure reporting, and the rule that key deletion occurs only after authenticated output is successfully written. No existing REC-02 cleanup or output test is evidence that secure deletion is implemented.

Zodiac’s static RSA format has no forward secrecy: if the recipient’s private key is later compromised, saved ciphertext could be exposed. For those files, I’d use a mature offline workflow such as age or SOPS, or a secrets manager. Age is specifically designed for file encryption and has a published format and established tooling.[age project (https://github.com/FiloSottile/age)](<https://github.com/FiloSottile/age>)

Email would carry the ciphertext, but still exposes message metadata. Gmail’s own client-side encryption, for example, leaves the subject, timestamps, and recipients outside that additional encryption.[Gmail CSE details](<https://support.google.com/mail/answer/13317990?hl=en>)


We could improve the lifecycle without changing Zodiac’s RSA and AES algorithms: use a **single-use RSA recipient keypair for each message**, generated and kept by the recipient, and encrypt to that key with the existing envelope. After successful decryption, the recipient discards the private key. That could protect already-decrypted messages from a later compromise of their regular key, **if the one-time private key was truly removed**.
