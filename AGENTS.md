# Repository instructions

## Purpose and sources

Build Zodiac Modern: a static Astro/Svelte 5 website that encrypts locally with native WebCrypto and presents celestial glyphs, plus a separate downloadable offline Go decrypt CLI. OpenSSL generates passphrase-encrypted private keys once; hosted code accepts public keys only.

Read `plan.md` and the relevant items in `backlog.md` before implementation. The user's current instructions take precedence. `context.md` contains historical alternatives and inaccurate security claims; `reference_impl.go.md` defines the compatible binary encryption envelope, not the website's deployment architecture. `tamar-recipes-main.zip` is an Astro/Svelte organization reference only.

This repository currently contains planning documents and reference assets. Do not describe planned commands, components, tests, or security reviews as already implemented or passed.

## Architecture

- Use Astro static output, Svelte **5**, strict TypeScript, and locally served assets. Keep static routes/layouts in Astro and browser state in small Svelte islands using runes.
- Keep page views, interactive islands, reusable UI, crypto, codecs, and exports in the directories specified in `plan.md`.
- No Sanity, React, SvelteKit server, encryption/decryption API, backend, database, analytics, remote fonts, remote scripts, telemetry, health polling, or service worker in the first release.
- Prefer CSS tokens and accessible native controls. Tailwind or shadcn-svelte requires a concrete benefit and compatibility with the enforced CSP; never add React shadcn packages.
- Use the current supported Astro/Svelte integration and Lucide Svelte package, verify compatible versions at setup, and pin the lockfile. Do not copy the ZIP's dependency list wholesale.
- Vercel is the primary static host; document Cloudflare Pages/Netlify alternatives and conditional Surge support. Generate headers from exact built hashes; Vercel static Build Output configuration must avoid stale/pre-evaluated root configuration. No provider runtime adapter/functions. Support pnpm dev and built local static serving with production headers, loopback by default.

## Security invariants

- Encrypt with a fresh 32-byte AES key per message, RSA-OAEP SHA-256/MGF1-SHA-256 with an empty label, a fresh 12-byte nonce, AES-256-GCM with a 128-bit tag, and AAD `wrappedKey || nonce`.
- Preserve the envelope **`wrappedKey || nonce || tag || ciphertext`**, then canonical unpadded Base64URL. WebCrypto returns `ciphertext || tag`; explicitly reorder it. No header, fingerprint, padding, compression, or glyph data inside this envelope.
- Support RSA-3072 and RSA-4096/e=65537. Website import accepts one PKIX/SPKI `PUBLIC KEY` PEM and rejects private/unsupported keys. The separate Go CLI imports the plan's encrypted PKCS#8 profile only, validates private RSA, and never sends it to the website.
- A production build requires an explicit recipient public key and expected fingerprint. Never generate a throwaway default key or ship a test key as a real recipient. Custom public keys remain in memory.
- No automatic message/history/AES/private/passphrase persistence, URLs/logs/SSR/network serialization. Static public-key props are permitted. Explicit user exports (ciphertext, artwork, CLI plaintext output) are supported and their persistence disclosed. Browser private-key generation/import/decryption is outside v1.
- Use native WebCrypto only for cryptographic primitives. Import AES keys as nonextractable; clear owned raw-key/plaintext byte buffers in `finally` and release references. JavaScript strings, browser internals, undo buffers, and garbage collection cannot provide guaranteed secure erasure.
- Validate lone UTF-16 surrogates in the original JS string before TextEncoder/byte counting; TextEncoder silently substitutes U+FFFD. Preserve valid UTF-8 exactly.
- Go CLI uses standard RSA/AES/GCM plus the repository-owned fixed-profile `receiver/internal/keyfile/pbes2.go` loader. This supersedes the old ban on handwritten PBES2 integration and third-party decoder choice. Use native crypto/pbkdf2 (API minimum Go 1.24; pin a currently supported patched toolchain), AES/CBC, encoding/asn1/pkix and x509. No third-party crypto/decoder import, algorithm registry, custom crypto/KDF/ASN.1 length parser, legacy x509.DecryptPEMBlock, OpenSSL subprocess or unencrypted-key fallback. youmark/pkcs8 and .NET runtime source are read-only references, with inspected commit provenance.
- Enforce the plan's exact PBES2/PBKDF2/explicit HMAC-SHA256-NULL/AES256-CBC profile and all bounds before KDF. Check complete consumption/exact fields inside every nested SEQUENCE with standard RawValue parsing; empty outer rest alone is insufficient. Distinguish absent key length from explicit zero. Scan all final-block bytes uniformly for PKCS#7 before strict inner PKCS#8/two-prime RSA validation. All key-unlock validation failures share one local error/exit 3; CBC key files are unauthenticated and glue is not automatically audited or constant-time.
- Use a hidden controlling-terminal prompt and only pinned/vendor-reviewed Go-maintained x/term/x/sys (including Windows ACL needs). No plaintext private temp files, secret argv/env/piped stdin, listener/API, automatic clipboard/editor or raw plaintext terminal output. Clear owned password/derived-key/full decrypted buffers on all paths; pbkdf2.Key takes a password string and returns an error, and immutable string/internal/key-integer/OS copies cannot be guaranteed wiped. No unsafe conversion or custom KDF to hide that limitation. Enforce 32-byte unwrap, authenticate before exclusive private output creation, reject overwrite/symlink/reparse escape and test Windows ACLs (0600 alone is insufficient on Windows).
- Treat symbol rendering as reversible presentation, not additional security. Keep raw ciphertext accessible. Freeze released icon paths and transport grammar; fail on unmapped characters rather than substituting a glyph.
- Sharing choice: primary Copy raw/Download ciphertext (.txt); secondary optional PNG artwork/full one-line SVG. V1 Go receiver consumes raw only; SVG metadata does not imply a v1 importer. A complete bounded compact-grid PNG can contain multiple archival pages' worth of glyphs (584 tokens fits one image); keep 512-token print/archival pages separate, and label partial-image fallback explicitly. Never imply art-only decryption, universal inline-SVG email support or PNG machine recovery. Unicode strings remain deferred.
- v1 exports trusted generated SVG only and restores raw/transcribed chunks only. No imported XML/SVG parser in website or CLI. Future SVG import is v1.1 (FUT-08), gated on bounded inert grammar, property/coverage fuzzing and independent review; never render/execute/fetch untrusted imports.
- Keep whole-envelope SHA-256 for final reassembly; add the specified `S64CHECK1` page/row check codes to localize transcription errors. Check labels/digests stay outside the compatible encrypted envelope and copied raw text; public checks are not authentication.
- Complete EN-04 self-contained file:// spike before selecting a native sender launcher. Prefer one fully bundled HTML if tested crypto/import/export/privacy/meta-CSP/fallbacks and independent verification UX pass; a normal Astro index referencing modules is not sufficient. Verify full HTML hash outside the file before opening against a trusted independent value; no self-verification badge or relaxed browser flags/CSP. Document meta-CSP/header limits and tested platforms. Pnpm local use remains supported.
- Deliver the selected reviewed sender artifact and signed Go receiver with per-file/final hashes/trusted publisher channel. Native sender launcher/signing is conditional fallback only; if selected, pin the asset manifest and serve confined loopback static files without key/message APIs. Receiver never listens. No updater or OS-warning bypass. Same-site hashes/TLS/badges do not close host/lookalike trust gaps; use verified local sender before sensitive typing when host is untrusted.
- Enforce style-src-attr 'none' without style attributes/Svelte style directives/transition-generated styles; use classes/SVG geometry attributes and inspect actual production DOM/exports. Keep worker-src 'none' synchronized with the no-worker scope.
- Do not claim unconditional zero knowledge, formal IND-CCA2 proof, constant-time JavaScript, FIPS certification, government approval, sender authentication, forward secrecy, or post-quantum security. Follow the exact security boundaries in `plan.md`.
- Adapt reference_impl.go.md envelope/OAEP/AAD/GCM logic for the Go CLI; remove HTTP/CORS/env/fallback setup, strengthen canonical decoding/32-byte key checks/bounds/output, and do not copy unchecked synthetic RNG or timing/blinding claims. Receiver/test tooling stays outside browser imports/hosted dist; downloads are separate signed artifacts.

## Development and validation

- Preserve the source reference files and ZIP. Do not import the ZIP's Sanity integrations, preview server, recipe content, or secrets.
- Existing flow PNGs are historical: encryption depicts a backend, and decryption incorrectly attributes blinding to `rand.Reader`. Exclude them from public docs and create corrected code-native diagrams; do not repeat those claims.
- Prefer `rg` for searches. Keep edits scoped, reversible, and reviewable. Do not access or request production private keys.
- Implement the agreed scripts before using them: formatting/type checks, unit tests, Go interoperability checks, browser tests, static build, and artifact/CSP checks. Exact commands are listed in `plan.md`.
- Start REC-01's isolated standard-library loader and real OpenSSL 3.0/3.5 fixtures in M0 alongside EN-01, before the EN-02 envelope harness/browser importer. First record real generated profile fields, both RSA sizes, expected success/rejection and OpenSSL oracle results; do not defer the prototype to M2. The 3.5 setup command explicitly sets -saltlen 16; a tested older generator does not justify accepting salts below the fixed 16-byte minimum. Test encrypted rewrapping/public-key equality rather than weakening policy.
- Security changes require meaningful tests: real browser WebCrypto plus independent Go decryption, tampering, UTF-8 boundaries, key validation, and network/storage checks. UI changes require keyboard, responsive, and print/export checks appropriate to their scope.
- Key loader tests require real OpenSSL differential fixtures/oracle, strict nested-schema/profile/padding/key cases, pre-KDF fuzzing with a test-only KDF stub/counter, bounded post-KDF fuzzing and independent glue review. Production always uses native PBKDF2. Optional .NET test oracle must decode PEM and require bytesRead equals full DER length; no shipped .NET dependency.
- The REC-01 fixture/oracle/negative/fuzz/resource/vendor/focused independent-review gates are mandatory for M0/REC-01 completion, remain CI/release gates and must not be postponed or waived for schedule. Record exact tools/fixture hashes/profile outcomes/fuzz runs/latency/reviewer findings, re-open affected evidence after relevant changes, and retain QA-03's separate integrated system review. A working prototype is not completion or an audit.
- Authenticate pinned Go module downloads and run go mod verify, then compare a clean regenerated vendor tree/file set/modules.txt against committed vendor, including extra files. go mod verify verifies the module cache, not vendor. Require unchanged go.mod/go.sum and offline -mod=vendor tests/builds with the pinned installed toolchain (GOTOOLCHAIN=local).
- Test the production build under enforced CSP; dev HMR is not evidence of production compatibility. Keep sensitive test traces/screenshots disabled unless they contain clearly synthetic data.
- Keep `backlog.md` statuses accurate. Mark work done only with its acceptance criteria and evidence satisfied; distinguish implementation completion from independent review and release gates.
- Record changes to wire formats, key policy, glyph alphabets, persistence, networking, or trust claims in the plan and tests before release.
- Run dev/preview servers in background or a managed terminal session. Keep helpers hidden on Windows. Stop only processes started for this task.

## Working style

Proceed with authorized implementation and routine verification without repeated permission requests. Ask only for information necessary to resolve a real dependency, such as the production recipient's **public** PEM and identity. Work without sub-agents unless the user explicitly requests delegation. Explain outcomes, validation, and material limits plainly.
